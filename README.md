# 字幕节奏与镜头边界校正台（Subtitle Rhythm & Shot-Boundary Correction Station）

本地运行的 Web 应用：导入 **SRT / WebVTT** 字幕与含镜头起止毫秒的 **JSON**，
按 **Unicode 扩展字素簇（UAX #29）** 计数，检查重叠、空隙、每秒字符数（CPS）
与跨镜头切换；在「只平移、不改时长」的前提下搜索确定性最优校正方案，
支持逐条采纳并导出带**原文哈希、校正版本、冲突说明**的 JSON。

## 技术栈

- 后端：Python 3.11 + FastAPI + SQLite（`fastapi` / `uvicorn` / `regex`）
- 前端：原生 HTML + CSS + JavaScript（无构建、无框架）
- 部署：Docker Compose 一键启动，数据持久化在命名卷中

## 一键启动（Docker Compose）

```bash
docker compose up -d --build
```

启动后浏览器访问：

> **http://localhost:8000/**

在页面中导入字幕与镜头 JSON 后即可查看字幕校正结果：统计条
（间隔/CPS/跨镜头/冲突数量）、逐条提案与 Δ、冲突链说明，并可逐条采纳、
导出 JSON / SRT / ZIP 校正结果。接口文档见 http://localhost:8000/docs 。

页面上若在一个标签页改参数的同时另一个标签页（或脚本）正在采纳，两个
写操作会在服务端自动排队：后提交的一方看到的始终是**另一方提交后的
最新状态**——先到的采纳若在新参数下失效会被自动撤销，先到的新参数会让
迟到的旧提案被拒绝；刷新后表格、统计条与导出的校正结果即与终态一致。
详见[下方「并发：参数更新与采纳交错」](#并发参数更新与采纳交错)。

停止：

```bash
docker compose down          # 保留数据卷
docker compose down -v       # 同时删除已导入的项目数据
```

SQLite 数据库位于容器内 `/data/subtitle_station.db`（Compose 命名卷
`subtitle-data`）。如需改用宿主机目录，可把 `docker-compose.yml` 的卷改成：

```yaml
volumes:
  - ./data:/data
```

## 本地直接运行（不使用 Docker）

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 数据库路径（可选，默认 ./subtitle_station.db 由 DATABASE_PATH 控制）

```

访问 http://localhost:8000/ ，接口文档在 http://localhost:8000/docs 。

## 使用流程

1. **导入素材**
   - 字幕：`.srt` 或 `.vtt`（自动识别；计数时去除标签、折叠空白，
     按扩展字素簇计数，空格计入字符，CJK 与 emoji 组合序列按 1 个可见字符计）。
   - 镜头 JSON（可选）：
     ```json
     [
       {"start_ms": 0,    "end_ms": 1200},
       {"start_ms": 1200, "end_ms": 3050}
     ]
     ```
     也接受 `{"shots": [...]}` 外层，字段名兼容 `start/end`、`in/out`、
     `start_ms/end_ms` 等毫秒字段。
2. **设置参数**
   - **CPS 上限**：每秒字符数告警阈值（平移不改变时长，CPS 仅作检测告警，
     无法通过平移修复时会在条目上标注）。
   - **最小间隔（ms）**：相邻条目之间允许的最小空隙；重叠（负值）与过小空隙
     都会被检出。
   - **镜头边界容差（ms）**：每个镜头**独立**参与判断（相接或重叠的镜头
     不做合并），条目整体必须落在某一个镜头内；起点可在 `原起点 ± 容差`
     内平移，且平移后条目不跨过镜头切点。原字幕一旦跨越切点即标记
     「跨镜头」，与容差无关；恰好始于或止于切点视为合法。
3. **查看结果**
   - 统计条：间隔/重叠、CPS、跨镜头、可提案、需移动、冲突数量与总移动量。
   - 表格逐行显示原文哈希、原时间、字素数、CPS、问题标记、提案时间与 Δ。
   - 无法满足约束的 cue 以**冲突链**形式列出（含导致失败的相邻关系说明）。
4. **逐条采纳**：每行「采纳 / 撤销」，或顶部「采纳全部提案」；采纳状态持久化。
5. **导出**
   - `JSON`：含项目参数、每条原文 SHA-256、`original` / `proposal` /
     `corrected` 三套时间、状态以及完整冲突说明，并带整包 `document_hash`。
   - `SRT`：导出采纳后的时间轴（未采纳者回退提案、再回退原值）。
   - `ZIP`：同时包含上述 JSON 与 SRT。

## 字幕时间轴的核对方法

页面与接口看到的时间轴始终遵循同一条**有效时间轴**规则：
**已采纳 → 提案 → 原值**（仅平移，时长永不改变）。可按下面方式核对：

1. **页面表格**：「当前时间」列对已采纳行显示采纳值，未采纳行显示原值；
   「提案」列显示新参数下的提案，「Δ」列是提案相对原起点的平移毫秒数；
   行首状态徽标为「已采纳 / 待采纳 / 冲突」。
2. **逐条核验**：对任意一条 cue，其导出时间应为
   - 已采纳：`adopted_start_ms / adopted_end_ms`（`corrected` 字段相同）；
   - 未采纳且有提案：`proposal_start_ms / proposal_end_ms`；
   - 冲突无提案：原始 `start_ms / end_ms`。
   时长 `end − start` 必须始终等于原时长。
3. **改参数后复核**：修改 CPS / 最小间隔 / 容差并提交后，表格与统计条会
   整体重算；不再合法的采纳自动变回「待采纳 / 冲突」。可用下方接口自行
   比对（以 `jq` 为例）：
   ```bash
   curl -s localhost:8000/api/projects/1 | jq '.analysis.cues[]
     | {cue_id, original:[.start_ms,.end_ms],
        proposal:[.proposal_start_ms,.proposal_end_ms],
        adopted:[.adopted_start_ms,.adopted_end_ms]}'
   ```
4. **两种 SRT 必须一致**：独立 SRT（`?fmt=srt`）与 ZIP 内的 `corrected.srt`
   使用同一条有效时间轴，字节级时间戳应完全相同；JSON 导出
   （`?fmt=json`）里每条的 `original / proposal / corrected` 三套时间
   分别保留原值、提案与**仅存的合法采纳**，`corrected` 为 `null` 即该条
   当前无有效采纳。
5. **典型用例**：导入 0–1000ms 与 1000–2000ms 两条字幕（最小间隔 40ms、
   容差 200ms），提案为 0–1000ms、1040–2040ms。只采纳第一条后再次用相同
   参数提交：第一条仍为「已采纳」；两种 SRT 中第一条是 0–1000ms，
   第二条是提案 1040–2040ms（而不是原值 1000–2000ms）。

## 参数变更与采纳状态重核验

更新 CPS 上限 / 最小间隔 / 边界容差时，系统会在**同一事务**内用新参数
重新核验每一条已采纳记录，核验规则与求解器约束一致：

- **仅平移**：新时长必须与原时长完全一致；
- **容差**：`|新起点 − 原起点| ≤ tolerance_ms`；
- **镜头边界**：平移后整体落在某一个镜头之内；
- **最小间隔**：与相邻条目的**生效位置**保持 `min_gap_ms`；生效位置与
  SRT 导出共用同一条有效时间轴——**已采纳取采纳值，未采纳先取新参数
  下的提案，无提案再取原值**（撤销一条后其邻居改按提案/原值重新参与
  核验，按轮次到达不动点）。

仍满足全部约束的采纳**保持有效**；不再满足的采纳被**撤销**，条目回到
「待采纳 / 冲突」状态。项目详情、项目列表、采纳按钮与 JSON / SRT / ZIP
三种导出统一使用重核验后的状态——失效的采纳时间不会出现在导出的
`corrected` 中。若重算过程失败，参数与采纳状态**整体回滚**，
不会留下半更新。

例如：镜头 `[0,1200)`、`[1200,2400)` 与 900–1300ms 字幕，容差 200ms 下
采纳提案 800–1200ms；把容差改为 50ms 后，该采纳因超出容差被撤销，
详情显示冲突链，三种导出的 `corrected` 均为空、时间轴回退原值。

又如：两条相接字幕 0–1000ms、1000–2000ms，最小间隔 40ms、容差 200ms，
提案为 0–1000ms、1040–2040ms。只采纳第一条（0–1000ms）后即使以**完全
相同的参数**再次提交，第一条也不会被误撤销：相邻的第二条未采纳，按其
提案 1040ms 参与间隔核验，1000→1040 恰为 40ms。

## 并发：参数更新与采纳交错

页面提交 `PUT /api/projects/{pid}/settings`（收紧容差或最小间隔）与
`POST /api/projects/{pid}/adopt`（按提案采纳）可能同时到达。两条写路径
都遵循**同一事务边界**：进入处理时先以 `BEGIN IMMEDIATE` 取得该库的
写锁，**然后**才读取项目参数、字幕、镜头与已采纳状态；参数读取、
`build_analysis` 提案求解、采纳核验与落库全部在这一个写事务内完成。
后到的请求在写锁上等待（忙等上限默认 30s，可用环境变量
`BUSY_TIMEOUT_MS` 调整），持锁方提交后在锁内**重读最新状态**再继续，
因此两种交错顺序都不会让新参数与失效采纳并存：

- **采纳先提交**：设置事务等到写锁后，读到的就是含该采纳的最新状态；
  用新参数求提案并经 `revalidate_adoptions` 重核验时，新参数下失效的
  采纳在同一事务内被撤销，仍合法的采纳保留。
- **设置先提交**：采纳事务等到写锁后，按新参数重新求解并校验；若请求
  携带的是旧参数下的提案位置、而新参数下已无此提案或位置改变，采纳被
  拒绝（`400`），不写入任何采纳记录。

任一步失败（求解异常、约束不合法等）都会整体回滚，参数与采纳状态
**不留半更新**。详情接口与 JSON / SRT / ZIP 导出同样在只读事务的
一致快照内读取与求解，呈现的永远是重核验后的状态，失效采纳不会进入
导出的 `corrected` 与 SRT 时间轴。并发回归见
`tests/test_concurrent_settings_adopt.py`（门控两种提交顺序）。

## 求解器说明（确定性最优）

对每一个与冲突链不相交的**连续可解后缀段**独立求解，搜索空间为各条目在
「单镜头窗口 ∩ 原起点 ± 容差」内的所有整数毫秒起点（每个镜头各自生成
窗口，相接镜头不合并，因此切点永远不可跨越），约束为：

- `t[i-1] + duration[i-1] + min_gap ≤ t[i]`
- 条目整体位于某一镜头窗口内（恰在切点开始/结束允许）
- 仅平移，`duration` 保持原值

项目详情、参数重算、页面标记与采纳校验均经由同一套 `build_analysis`
规则实时重算，任何入口看到的跨镜头标记、提案与冲突链完全一致。

采用整数区间上的**分段线性动态规划（后缀极小包络）**精确求解，择优按
字典序严格排列：

1. **总移动毫秒** `Σ|t_i − original_i|` 最小；
2. 并列时，**发生移动的条目数**最少；
3. 再并列时，按 **`cue_id` 字典序**排列的绝对偏移向量字典序最小
   （越靠前的 cue_id 越优先保持原位；正负向偏移相同时取较小起点）。

权值采用超递增整数系数（Python 大整数精确运算，无浮点比较），
因此相同输入永远产生唯一、确定的输出。不存在可行解的条目归入**冲突链**：
链是连续的不可解段，说明中给出硬阻断的相邻 cue 对或“无镜头窗口可容纳”等
内在冲突原因。

```

  shots.py       镜头 JSON 解析
  analysis.py    检测编排（重叠/空隙/CPS/跨镜头）与统计
  corrector.py   分段线性 DP 求解器与冲突链构造

tests/           全枚举等价性测试与性能冒烟测试
docker-compose.yml / Dockerfile
```
